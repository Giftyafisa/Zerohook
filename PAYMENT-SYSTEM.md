# Zerohook Payment System — How It Works

## Overview

Zerohook uses a **fee-free, crypto-only payment system** with no third-party payment gateways (no Paystack, no Stripe, no Coinbase Commerce). All payments go through direct blockchain transactions verified via free public APIs.

Users pay in cryptocurrency. The platform takes a **5% fee** on escrow releases. There are **zero payment gateway fees** — only standard blockchain network (gas) fees apply.

---

## Where Does the Money Go? (Whose Wallet?)

### HD Wallet Architecture

The platform uses a **single master seed phrase** (BIP39 mnemonic) stored in the environment variable `CRYPTO_MASTER_SEED`. From this one seed, the system derives **a unique new address for every transaction** using HD (Hierarchical Deterministic) wallets:

| Crypto | Derivation Path | Standard |
|--------|----------------|----------|
| BTC | `m/84'/0'/0'/0/{index}` | BIP84 (native SegWit) |
| ETH / USDT / USDC | `m/44'/60'/0'/0/{index}` | BIP44 |

The derivation index is stored persistently in MongoDB (`SystemCounter` collection) so it survives server restarts and never reuses an address.

### Who Controls the Money?

**YOU (the site owner) control ALL the money.** Here's why:

1. **You own the master seed** (`CRYPTO_MASTER_SEED` in your `.env` file). Every payment address generated by the platform is derived from this seed.
2. **You can import the seed into any standard HD wallet** (Electrum, MetaMask, Trust Wallet, Ledger, etc.) and gain full access to every address the platform has ever generated.
3. All BTC, ETH, USDT, and USDC that users deposit **lands on addresses you control**.
4. The platform also has explicit **platform wallet addresses** in your `.env`:
   - `PLATFORM_BTC_ADDRESS` — your BTC receiving address
   - `PLATFORM_ETH_ADDRESS` — your ETH/ERC-20 receiving address

### What Happens When Addresses Are Generated Randomly (No Seed)?

If `CRYPTO_MASTER_SEED` is not set, the system falls back to **random key generation**. In this mode:
- BTC: Random keypair via `crypto.randomBytes(32)` + secp256k1
- ETH: `ethers.Wallet.createRandom()`

⚠️ **WARNING**: Random addresses mean **you cannot recover funds** sent to them unless you store the private keys separately. Always set `CRYPTO_MASTER_SEED` in production.

## Payment Flows

### Flow 1: Wallet Deposit (Top Up)

```
User clicks "Deposit" → Picks crypto (BTC/ETH/USDT/etc.) → Enters fiat amount
    ↓
Backend converts fiat → crypto via live CoinGecko rates
    ↓
CryptoPaymentManager generates a unique address from HD wallet
    ↓
Invoice saved to MongoDB (CryptoInvoice collection) — expires in 30 minutes
    ↓
Frontend shows address + amount + QR code → User sends crypto from their personal wallet
    ↓
Frontend polls /payments/verify-inline every 10 seconds
    ↓
Backend checks blockchain via Blockstream (BTC) or Etherscan (ETH/ERC-20)
    ↓
Once confirmed → Transaction marked 'completed' → Wallet balance updated
```

**The crypto lands on a platform-controlled address derived from your master seed.**

### Flow 2: Escrow Payment (Service Booking)

```
Client books a service → Creates escrow hold
    ↓
If payment method = 'wallet':
    Client's wallet balance is checked (deposits + escrow_releases - withdrawals - held)
    Amount is held as 'escrow_hold' transaction (status: 'held')
    ↓
If payment method = 'crypto':
    Same as deposit flow — crypto invoice generated, user pays to HD-derived address
    ↓
A 6-digit PIN is generated and given to the client ONLY
    ↓
Service happens in real life
    ↓
Client shares PIN with provider → Provider enters PIN on the app
    ↓
PIN verified → Status changes to 'pin_entered'
    ↓
Client has 48 hours to either:
  (a) Confirm → Funds released immediately
  (b) Dispute → Admin reviews
  (c) Do nothing → Auto-release after 48 hours
    ↓
On release:
  - 5% platform fee deducted
  - 95% credited to provider's wallet as 'escrow_release' transaction
  - Platform fee stored in transaction metadata
```

**Provider gets 95%. Platform keeps 5%. No money actually leaves the blockchain — it's all virtual wallet balances tracked in MongoDB.**

### Flow 3: Subscription Purchase

```
User picks a plan → Selects crypto (BTC/ETH/USDT/etc.)
    ↓
Backend converts subscription price → crypto via live rates
    ↓
CryptoPaymentManager generates unique address
    ↓
User sends payment → Blockchain verification → Subscription activated for 6 months
```

**Subscription payments go to HD-derived addresses. 100% of subscription revenue is yours.**

### Flow 4: Withdrawal (User Cashes Out)

```
User requests withdrawal → Enters amount + their destination crypto address
    ↓
Backend validates balance, creates 'withdrawal' transaction (status: 'pending')
    ↓
Admin reviews via /api/admin/withdrawals
    ↓
Admin approves → Manually sends crypto from platform wallet to user's address
    ↓
Admin marks as completed with blockchain tx hash
```

**Withdrawals are MANUAL. You (admin) physically send crypto from your wallet to the user's address. This is by design — gives you full control.**

## The Virtual Wallet System

User balances are **not real blockchain balances**. They are calculated from MongoDB transaction records:

```
Available Balance = (deposits + escrow_releases) - (withdrawals) - (escrow_held)
```

Transaction types:
| Type | Description | Effect on Balance |
|------|-------------|-------------------|
| `deposit` | User sends crypto to platform | +amount |
| `wallet_topup` | Same as deposit (alias) | +amount |
| `escrow_hold` | Client books a service | -amount (locked) |
| `escrow_release` | Service completed, provider paid | +amount (to provider, after 5% fee) |
| `withdrawal` | User withdraws to their wallet | -amount |
| `payment` | Direct payment | -amount |
| `admin_fee_withdrawal` | Admin withdraws collected fees | (admin only) |

## Platform Revenue — How You Get Paid

### Revenue Sources

1. **Escrow Fees (5%)**: Every time an escrow is released, 5% is deducted. This is stored in `metadata.platformFee` on the `escrow_release` transaction.

2. **Subscription Revenue (100%)**: Every subscription payment goes entirely to your HD wallet addresses.

### How to Access Your Revenue

You need `is_admin: true` or `role: 'admin'` set on your MongoDB user document.

#### 1. View Revenue Dashboard
```
GET /api/admin/revenue
Authorization: Bearer <your-token>
```
Returns:
- Total platform fees (all-time + last 30 days)
- Subscription revenue
- Active subscription count
- Pending user withdrawals awaiting your approval
- Total transaction volume

#### 2. Withdraw Your Platform Fees
```
POST /api/admin/withdraw-fees
Authorization: Bearer <your-token>
Body: {
  "amount": 500,
  "destinationAddress": "0xYourPersonalWallet...",
  "cryptoSymbol": "USDT",
  "notes": "Monthly fee withdrawal"
}
```
This creates a record tracking how much you've withdrawn from fees. The actual crypto is already sitting on your HD wallet addresses — you move it yourself.

#### 3. Process User Withdrawals
```
POST /api/admin/withdrawals/:id/approve
Body: { "txHash": "0xblockchain_tx_hash..." }

POST /api/admin/withdrawals/:id/reject
Body: { "reason": "Suspicious activity" }
```

### The Key Insight: All Crypto Is Already In Your Wallet

Since every payment address is derived from YOUR master seed:
- All deposits, subscription payments, and escrow payments are **already in addresses you control**
- The MongoDB "wallet balance" is just an accounting ledger
- When a user withdraws, you send crypto from your wallet to theirs
- Platform fees don't need to be "collected" — they're already yours. The admin routes just track the accounting.

## Environment Variables You MUST Set

```env
# CRITICAL — Your master wallet seed. Whoever has this controls ALL funds.
CRYPTO_MASTER_SEED=your 24-word bip39 mnemonic phrase here

# Generate one with: node -e "console.log(require('bip39').generateMnemonic(256))"

# Network (use 'mainnet' for production, 'testnet' for development)
BITCOIN_NETWORK=mainnet

# Ethereum RPC for transaction verification
ETHEREUM_RPC_URL=https://eth-mainnet.g.alchemy.com/v2/your-key

# Optional but recommended for faster ETH verification
ETHERSCAN_API_KEY=your-free-etherscan-api-key

# Your personal receiving addresses (for display/reference)
PLATFORM_BTC_ADDRESS=bc1q...your_btc_address
PLATFORM_ETH_ADDRESS=0x...your_eth_address

# Fee percentage (default: 5)
PLATFORM_FEE_PERCENT=5
```

## Security Notes

1. **NEVER share or commit `CRYPTO_MASTER_SEED`** — it controls all funds on the platform
2. **Back up your seed phrase offline** (paper, metal plate, hardware wallet)
3. Withdrawals are manual — you physically review and send each one
4. Admin access requires `is_admin: true` on the MongoDB user document (not just a high verification tier)
5. Invoice data persists in MongoDB (`CryptoInvoice` collection) so payments aren't lost on server restart
6. The derivation index (`SystemCounter` collection) is atomic and persistent — addresses are never reused
